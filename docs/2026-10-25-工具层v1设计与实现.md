## 1. 项目背景与目标

### 1.1 作业要求（摘自 PPT）

开发一个基于 LLM 的 **C/C++ 函数代码漏洞检测 Agent**，输入单个函数与对应代码仓库链接，输出：

1. 检测函数 `idx`
2. 检测结果（有漏洞 / 无漏洞）
3. 判定理由
4. 分析记录（知识库检索记录 + 仓库读取记录）

必须提供**图形化 UI**，支持单样本检测与 `.jsonl` 批量检测。

### 1.2 两个核心难点 → 两条技术主线

| 难点 | 对策 |
|---|---|
| LLM 缺乏软件安全领域知识 | 用历史 CVE 案例构建领域知识库，做 RAG 检索 |
| 孤立函数不足以判断安全性（漏洞常与调用方/被调用方/全局变量相关） | 给 Agent 在代码仓库中**按需挖掘上下文**的能力 |

### 1.3 三条红线

1. **必须是自主 Agent**：不能封装成 skill 调用 Codex / Claude Code 等商业工具，也不能退化成无决策的多步 LLM API 串行。
2. **严格成对隔离**：不能同时提供漏洞版与修复版；仓库只能提供对应一个版本；不得暴露 `git diff`。
3. **禁止网络搜索**：除按 `commit_url` 获取指定版本仓库外，不提供其他联网能力。

### 1.4 评价方法

150 对（300 条）样本，按成对统计：

| 类型 | 含义 |
|---|---|
| **P-C** | 漏洞版→1、修复版→0（完美区分，核心指标） |
| P-V | 均判 1（漏报修复版） |
| P-B | 均判 0（漏报漏洞版） |
| **P-R** | 完全反转（惩罚项） |

等级：A ≥30 对、B 25~29、C 20~24、D <20；若 `P-R > P-C/2` 则降一级。

## 2. 系统架构

### 2.1 数据流

```
[前端]
  单样本表单 ─┐
  .jsonl 上传 ─┴─→ POST /tasks
                    ↓
[API / 任务层]  校验字段、落盘、生成 task_id、开 SSE 通道
                    ↓
[样本加载器 SampleLoader]        ← label 在这里消费掉，不往下传
  1. 校验 idx / commit_url / target / func
  2. 版本解析：label=1 → sha = C^ ，label=0 → sha = C
  3. 产出最小化的 AgentInput（含 allowed_sha）
                    ↓
[Agent 层]
  ① retrieve_knowledge(func) → RAG top-k 历史案例
  ② 初步分析 → 形成假设 +「还缺什么证据」清单
  ③ 证据不足 → 调工具 grep / find / read_file / list_dir
         ↓（首次调用时惰性物化，Agent 无感知）
  [RepoFS 仓库工具层]
    - 校验目标 path 属于 allowed_sha
    - ensure_snapshot(owner, repo, sha)：命中缓存 or 下 tarball
    - 返回内容 + 自动写 read_log
  ④ 证据足够 / 预算耗尽 → 结构化判定（JSON Schema 约束）
                    ↓
[报告层]  拼装四要素 → 报告对象 & result.jsonl
                    ↓
[前端]   SSE 实时渲染「检索→思考→读了哪个文件→结论」
```

离线侧两条独立支线：**建知识库**（一次性）与 **evaluate.py 评测**，都不在请求链路上。

### 2.2 架构图

文件：`docs/assets/architecture.drawio`（可用 draw.io 打开编辑）

### 2.3 三条设计原则

| 原则 | 落点 |
|---|---|
| **加载器做裁剪** | `label` 与修复信息止步于 `SampleLoader`，不进入 Agent 视图 |
| **Agent 只决定"查什么"** | 下载、解压、缓存是工具层的透明副作用，Agent 不感知 |
| **约束写在代码里，不写在提示词里** | `allowed_sha`、预算、日志均由系统强制 |

## 5. 工具层实现

### 5.1 `tool/workspace.py` — 沙箱原语

#### 5.1.1 类定义

```python
class Workspace:
    def __init__(
        self,
        root: str | os.PathLike[str],
        *,
        read_only: bool = True,
        max_read_bytes: int = 2 * 1024 * 1024,
    ) -> None: ...
```

| 属性 | 含义 |
|---|---|
| `root` | 已 `resolve()` 的绝对路径，所有操作的上界 |
| `read_only` | 默认 `True`。检测阶段的工作区是某个 commit 的快照，只应被读 |
| `max_read_bytes` | 单文件按文本读取上限，超过则退化为流式窗口 |

#### 5.1.2 方法清单

| 方法 | 作用 | 关键点 |
|---|---|---|
| `read_file(path, offset=1, limit=300)` | 按行读取，返回**带行号**内容 | 1-based offset；二进制拒绝；大文件流式 |
| `list_dir(path=".", recursive=False, max_depth=2)` | 列目录 | 默认跳过隐藏项与 `.git` 等噪音目录 |
| `find_files(pattern, max_results=200)` | 按文件名/相对路径通配查找 | 对应 PPT 的 `find` |
| `exists(path)` | 是否存在 | 越界仍抛错，不静默返回 False |
| `stat(path)` | 类型 / 大小 / mtime | — |
| `write_file(path, content, ...)` | 写文本 | 只读工作区直接拒绝 |

#### 5.1.3 路径沙箱（核心）

```python
def _resolve(self, path: str) -> Path:
    raw = str(path).strip().replace("\\", "/")
    if not raw:
        raise PathViolation("路径不能为空；表示根目录请用 '.'")

    # 1) 拒绝绝对路径与盘符
    if raw.startswith("/") or raw.startswith("~"):
        raise PathViolation(...)
    if len(raw) > 1 and raw[1] == ":":
        raise PathViolation(...)

    # 2) resolve() 展开 .. 与软链接，任何逃逸都会在这里现形
    target = (self.root / raw).resolve()
    if not self._is_inside(target):
        raise PathViolation(f"路径越出工作区：{path}")
    return target
```

`_is_inside()` 使用 `os.path.normcase` 比较，兼顾 Windows 大小写不敏感与路径分隔符差异：

```python
def _is_inside(self, target: Path) -> bool:
    if target == self.root:
        return True
    root = os.path.normcase(str(self.root))
    child = os.path.normcase(str(target))
    return child.startswith(root + os.sep)
```

#### 5.1.4 异常体系

```
WorkspaceError
├── PathViolation        # 路径越界 / 绝对路径 / 空路径
├── NotFound             # 路径不存在
├── NotAFile             # 期望文件，实际是目录
├── NotADirectory        # 期望目录，实际是文件
├── BinaryFile           # 含 NUL 字节，拒绝按文本读
└── ReadOnlyViolation    # 只读工作区上写
```

#### 5.1.5 返回值格式

统一为可 JSON 序列化的 `dict`，便于直接写入 trace 与报告。

```json
{
  "path": "src/a.c",
  "start_line": 3,
  "end_line": 4,
  "total_lines": 10,
  "truncated": true,
  "size_bytes": 12834,
  "content": "3: line3\n4: line4"
}
```

**行号前缀（`3: `）是刻意设计**：让 Agent 的引用能落到具体行，报告里可核对，避免"我看了这段代码"这种无法验证的表述。

### 5.2 `tool/file_tools.py` — LangChain 适配层

```python
def build_file_tools(workspace: Workspace) -> list:
    @tool
    def read_file(path: str, offset: int = 1, limit: int = 300) -> str:
        """读取工作区内一个文本文件，返回带行号的内容。..."""
        try:
            return _ok(workspace.read_file(path, offset=offset, limit=limit))
        except WorkspaceError as exc:
            return _err(exc)
    ...
    return [list_dir, read_file, find_files, stat, write_file]
```

这一层只做三件事：

1. **绑定依赖**：用闭包捕获 `workspace`，使其不出现在工具签名（即 LLM 可见的 schema）里；
2. **异常转文本**：`ERROR: ...`，避免一次越界读打断整个 loop；
3. **JSON 序列化**：`_ok()` 一处收敛，trace 与报告复用同一份结构。

### 5.3 五个工具一览

| 工具 | 作用 | 参数 |
|---|---|---|
| `list_dir` | 看目录结构，先摸清仓库布局 | `path`、`recursive`、`max_depth` |
| `read_file` | 读文本，返回带行号内容 | `path`、`offset`、`limit` |
| `find_files` | 按文件名/路径通配查找 | `pattern`、`max_results` |
| `stat` | 确认存在性、大小、mtime | `path` |
| `write_file` | 写报告/笔记；只读工作区下报错 | `path`、`content` |

### 5.4 `tool/__init__.py` — 懒加载导出

```python
def __getattr__(name: str):
    """让 build_file_tools 按需导入，避免没装 langchain 时整个包不可用。"""
    if name in {"build_file_tools", "FILE_TOOL_NAMES"}:
        from . import file_tools
        return getattr(file_tools, name)
    raise AttributeError(...)
```

目的：**不让"装了 langchain"成为"能读文件"的前提**。核心层可独立测试、可被评测脚本直接调用。

## 6. 关键设计决策

| # | 决策 | 理由 |
|---|---|---|
| 1 | 沙箱是首要目标，不是"能读文件" | 路径逃逸、软链逃逸、盘符路径全部拦截；为后续成对隔离打地基 |
| 2 | `read_only=True` 作为默认值 | 若允许写，Agent 可能改掉证据再"分析"；产出物应显式开另一个可写工作区 |
| 3 | 异常分层：核心抛、工具吞 | 核心层可测、可被脚本调用；工具层容错，Agent 拿到可读错误后可重试 |
| 4 | 读文件带行号 | 让引用可核对，报告可追溯 |
| 5 | 大文件流式读取 | 超过 2MB 只取窗口，`total_lines` 返回 `null` 而非编造 |
| 6 | 实例 = 版本 | 一个 `Workspace` 绑定一个 sha，隔离靠"对象不存在"而非"调用方记得别传错" |
| 7 | 工具用闭包绑定工作区 | `@tool` 签名即 LLM 可见的能力清单，运行时依赖绝不能出现在签名里 |
| 8 | 每个工作区一套独立工具对象 | 只读 + 各自持有 root，批量并发无需加锁，也不可能跨样本污染 |

## 7. 使用方式

### 7.1 核心层（不经 LLM）

```python
from tool import Workspace

ws = Workspace(f".cache/{owner}/{repo}/{sha}")   # 只读快照
info = ws.read_file("src/net.c", offset=100, limit=50)
print(info["content"])
```

### 7.2 工具层（接入 Agent）

```python
from langgraph.prebuilt import create_react_agent
from tool import Workspace, build_file_tools

ws = Workspace(f".cache/{owner}/{repo}/{sha}", read_only=True)
tools = build_file_tools(ws)

agent = create_react_agent(model, tools)
result = agent.invoke({"messages": [("user", prompt)]})
```

### 7.3 成对隔离的正确姿势

```python
ws_vuln  = Workspace(f".cache/{repo}/{sha_parent}")   # 标签 1
ws_fixed = Workspace(f".cache/{repo}/{sha_commit}")   # 标签 0

# 每个样本各自构建工具，两套工具互不可见
tools_vuln  = build_file_tools(ws_vuln)
tools_fixed = build_file_tools(ws_fixed)
```

> ⚠️ 绝不要复用同一个 `Workspace` 实例跨样本切换 root —— 那会让"隔离"退化成"调用约定"。

## 9. 已知限制

| 限制 | 影响 | 计划 |
|---|---|---|
| 无 `grep`（内容检索） | Agent 只能按文件名查找，定位符号效率低 | 下一步补齐 |
| 无快照获取 | 需手动准备本地目录 | 由 RepoFS 层封装 tarball |
| 无总预算控制 | 理论上可无限次调工具 | 在 loop 层加 `max_steps` / `max_read_chars` |
| 单文件读取按 UTF-8 解码 | 非 UTF-8 源码（如 GBK）会出现替换字符 | 后续可加编码探测 |
| 大小写判断依赖 `normcase` | Windows 下正确，Linux 下为恒等 | 可接受（Linux 本身区分大小写） |

## 10. 下一步路线

按"能跑通 → 更好用 → 可评测"的顺序推进，不提前堆功能。

### 第 1 步：最小 Agent Loop（当前优先）

- 用一个**已解压的本地快照** + 一个真实函数跑通：
  `list_dir → read_file → 结论`
- 打印全部 messages，观察：调了几次工具、读了哪些文件、是否在"不需要读仓库"的样本上过度探索
- 重点调**提示词里的"证据足够就停"**，这比加功能更重要

### 第 2 步：补 `grep`

- 复用 `Workspace._resolve`，不重写路径校验
- 支持正则、上下文行数、结果上限、命中行号
- 这是 PPT 明确要求的工具，也是 Agent 最常用的

### 第 3 步：RepoFS 快照层

- `ensure_snapshot(owner, repo, sha)`：`codeload.github.com/o/r/tar.gz/<sha>`
- 缓存按 `{owner}/{repo}/{sha}` 分片，两版本物理隔离
- 对 Agent 透明：首次 `grep`/`read_file` 时惰性物化
- `Workspace` 内加 `_ensure_local()`，工具层与测试零改动

### 第 4 步：RAG 知识库

- 离线构建：CVE 案例 → 向量化 → FAISS / Chroma
- 在线检索：`retrieve_knowledge(func)` 返回 top-k 案例
- 红线：只能使用提供的数据集，不得引入额外安全知识

### 第 5 步：报告层与评测

- 四要素报告；`read_log` / `retrieve_log` **由系统 trace 生成**，不由模型自述
- `result.jsonl`（`idx` + `prediction`）
- `evaluate.py` 成对统计 P-C / P-V / P-B / P-R

## 附录 A：设计问答原文（为何定义 Workspace 类、为何用闭包构建工具集）

> 以下为 2026-10-25 的问答原文，未经修改，便于后续复查设计意图。

好问题。这两处都不是"面向对象习惯"，而是被**安全隔离**和**框架约束**逼出来的。核心一句话：

> **`Workspace` 负责"能做什么"（能力边界），闭包负责"用哪个工作区做"（依赖绑定）。**

---

# 一、为什么要定义 `Workspace` 类

## 1. 三个状态必须绑在一起，不能各传各的

```python
self.root          # 沙箱根目录（resolve 过）
self.read_only     # 是否允许写
self.max_read_bytes
```

如果写成自由函数，每个函数都要收 `root`：

```python
def read_file(root, path, ...)
def list_dir(root, path, ...)
def find_files(root, pattern, ...)
```

问题不在于"多写几个参数"，而在于**不变量（invariant）无处安放**：

- `root` 必须 `resolve()` 一次，之后所有比较都基于这个规范化结果。散成自由函数后，每个函数自己 resolve，**总有一个会忘**；
- `read_only` 是策略，不该由调用方每层传一遍 —— 传着传着就漏了，某个分支没传就默认成可写。

类的本质是**把"共享的不变量"钉死在一个构造点**：构造时校验一次，之后所有方法都活在同一个前提下。

## 2. 安全校验必须只有一个入口

这是最关键的一条。你现在只有一个 `_resolve`：

```python
def _resolve(self, path: str) -> Path:
    raw = str(path).strip().replace("\\", "/")
    if raw.startswith("/") or raw.startswith("~"):   raise PathViolation(...)
    if len(raw) > 1 and raw[1] == ":":               raise PathViolation(...)
    target = (self.root / raw).resolve()             # 展开 .. 和软链
    if not self._is_inside(target):                  raise PathViolation(...)
    return target
```

现在想象**没有 Workspace**，你要加 `grep`：

```python
def grep(root, pattern):        # 又来一份路径拼接逻辑
    file_path = Path(root) / user_path   # ← 这里忘了 resolve
```

这是真实项目里最常见的漏洞形态：**安全逻辑复制了 N 份，其中一份写错了**。而有了类，`grep` 只需要：

```python
target = self._resolve(path)   # 白拿全部防护
```

**一份实现，所有工具共享。** 你后面加的 `grep`、`read_symbol`、`fetch_snapshot` 全部继承这套防护，不需要重新论证安全性。

## 3. 实例 = 版本，隔离靠"对象不存在"

这直接对应 PPT 的成对隔离红线。两种写法对比：

```python
# ❌ 参数式：隔离靠"调用方记得别传错"
tools = build_tools(root="/cache/openssl/" + sha)

# ✅ 实例式：隔离靠"另一个对象根本没被创建"
ws = Workspace(f"/cache/openssl/{sha}", read_only=True)
tools = build_file_tools(ws)
```

前者只要有一次传错 sha，或者缓存目录被复用，漏洞版就看到了修复版代码 —— 而**这种错误在日志里看不出来**，因为它是一次合法调用。

后者是结构性的：那个 `Workspace` 对象的 `root` 从构造起就固定，`resolve` 之后连软链接都出不去。**Agent 无论怎么努力，都无法表达"我想看另一个 sha"这个请求** —— 因为工具签名里根本没有这个参数。

安全设计里有个原则：**能靠"表达不出来"解决的，不要靠"检查后拒绝"解决。** 前者不会因为代码改动而失效。

## 4. 它能被替换，这是为后面几步留的伏笔

现在 `Workspace` 是"本地一个已解压目录"。但你后面要做**按需下载快照**。最干净的做法是让 `Workspace` 自己变懒：

```python
class Workspace:
    def _ensure_local(self, target: Path) -> None:
        if not target.exists():
            self._materialize(target)      # 按需拉这个文件/这棵子树
```

然后 `read_file` / `list_dir` 里加一行 `self._ensure_local(target)`。

**工具层、Agent 层、测试全部零改动。** 因为对它们来说，"工作区"一直只是一个 `read_file(path)` 的抽象，底下是本地目录还是远端按需拉取，与它们无关。

如果不封类，这个演进会变成：改 5 个工具的函数签名，改所有调用点，改所有测试。**封装的价值不在"现在好写"，在"以后好改"。**

## 5. 核心层不依赖框架

`workspace.py` 里没有一行 `import langchain`。这带来三个实际好处：

- 测试跑得快（1.3 秒 42 项），不需要构造模型；
- PPT 说技术栈不限定，万一你后面想换 AutoGen 或自写 loop，核心层不用动；
- 报告/评测脚本可以直接 `Workspace(...).read_file(...)`，**不经过 LLM** —— 比如 `evaluate.py` 要核对某个样本的函数体，走这里比走工具层干净。

这也是 `tool/__init__.py` 里用 `__getattr__` 懒加载的原因：**不让"装了 langchain"成为"能读文件"的前提**。

# 二、为什么要用闭包构建工具集

## 1. 根本原因：`@tool` 的函数签名会被翻译成给 LLM 的 schema

LangChain 的 `@tool` 会用**类型注解 + docstring** 生成参数 schema。所以：

```python
@tool
def read_file(path: str, offset: int = 1) -> str:
    """..."""
```

模型看到的参数就是 `{path, offset}`。**签名里出现什么，模型就能控制什么。**

于是关键问题来了：`Workspace` 放哪？

| 放法 | 结果 |
|---|---|
| 作为参数 `def read_file(ws: Workspace, path: str)` | ❌ **灾难**：模型可以自己指定工作区对象。隔离彻底失效 |
| 模块级全局 `GLOBAL_WS` | ❌ 300 条批量跑要不停 `set_root`，串行也会因为忘记重置而串版本，并发直接竞态 |
| `functools.partial(impl, ws)` 再套 `@tool` | ❌ partial 没有正确的 `__name__`/签名，schema 会乱 |
| **闭包** | ✅ 依赖不在签名里，模型只能传 `path` |

闭包做的事只有一件：

```python
def build_file_tools(workspace: Workspace) -> list:
    @tool
    def read_file(path: str, offset: int = 1, limit: int = 300) -> str:
        """读取工作区内一个文本文件..."""
        try:
            return _ok(workspace.read_file(path, offset=offset, limit=limit))
        except WorkspaceError as exc:
            return _err(exc)
    ...
    return [read_file, ...]
```

`workspace` 通过**词法作用域**被捕获，对模型完全不可见。模型能表达的只有"读哪个文件"，**永远表达不出"读哪个仓库"**。

这就是第一部分的第 3 点说的"表达不出来"原则，在工具层的落地。

## 2. 一个实例一套工具，天然并发安全

```python
ws_a = Workspace(f".cache/{repo}/{sha_vuln}")
ws_b = Workspace(f".cache/{repo}/{sha_fixed}")
tools_a = build_file_tools(ws_a)
tools_b = build_file_tools(ws_b)
```

`tools_a` 和 `tools_b` 是**两组互相不知道对方存在的函数对象**。批量跑 300 条时，无论串行还是多线程，都不需要任何锁 —— 因为它们只读，且各自持有自己的 root。

对比全局单例：你必须保证"用完一个样本再切下一个"，一旦为了性能改成并发，就得加锁，而锁的粒度稍有不慎就是**跨样本污染**。

我在测试里专门锁了这一点：

```python
def test_each_workspace_gets_isolated_tools(tmp_path):
    tools_a = build_file_tools(Workspace(a))
    tools_b = build_file_tools(Workspace(b))
    assert find(tools_a) == 1     # a 有文件
    assert find(tools_b) == 0     # b 看不到
```

## 3. 为什么用工厂函数而不是 `BaseTool` 子类

技术上等价，但收益不同：

```python
class ReadFileTool(BaseTool):
    name = "read_file"
    ws: Workspace          # ← pydantic 字段，会进 schema/序列化
    def _run(self, path: str): ...
```

- LangChain 的 `BaseTool` 是 pydantic 模型，`ws` 作为字段会被纳入校验模型，还得处理 `arbitrary_types_allowed`；
- 工具数量一多，5 个类 × 样板代码，噪音远大于收益；
- 闭包版本里，**每个工具的"业务逻辑"只有一行 `workspace.xxx(...)`**，读起来就是一张能力清单。

而 `@tool` 的 docstring → schema 机制，正是我们希望模型读到"这个工具什么时候该用"的地方 —— 类式写法反而绕开了它。

## 4. 顺带解决的两件小事

**错误不让 loop 崩**：

```python
except WorkspaceError as exc:
    return _err(exc)      # "ERROR: 路径越出工作区：../../secret"
```

Agent 拿到的是一个可读的失败信息，可以换个路径重试；如果直接抛异常，整个图就中断了。**工具层负责容错，核心层负责正确** —— 这也是为什么异常在 `workspace.py` 里抛、在 `file_tools.py` 里吞。

**返回值统一 JSON**：`_ok()` 一处收敛，后面 trace 和报告直接消费同一份结构，不用为"工具结果"和"内部调用"写两套序列化。

---

# 三、这么写的代价（诚实说）

| 代价 | 说明 | 是否可接受 |
|---|---|---|
| 多一层抽象 | 5 个工具要经过 `build_file_tools` | ✅ 收益远大于成本 |
| 闭包不可 pickle | 若以后要跨进程/持久化工具对象会麻烦 | ✅ 依赖是运行时的，本来也不该序列化 |
| 调试时闭包变量看不见 | 出错时不知道 `workspace.root` 是啥 | ✅ 在 `build_file_tools` 入口打一行日志即可 |
| 小脚本显得重 | 如果只读一个文件，类确实多余 | ✅ 本项目不是小脚本 |

**什么时候不该这么写**：工具无状态、没有共享不变量、也不会增长 —— 那就直接写函数，别为了"架构感"封类。这里之所以值得，是因为你**确定**后面要加 `grep`、`read_symbol`、懒加载快照，而它们必须共享同一套路径校验。

---

# 四、一句话总结

- **`Workspace` 类**：把 `root + read_only + 路径校验` 这三个不变量钉在一个构造点，让后续每个工具**白拿**安全保证，并且给"本地快照 → 按需拉取"留了一个零改动的演进口。
- **闭包工厂**：因为 `@tool` 的签名就是给模型的能力清单，**运行时依赖绝不能出现在签名里**。闭包把 `workspace` 焊死在函数内部，模型只能表达"读哪个文件"，无法表达"读哪个版本" —— 隔离从"检查"变成"不可能"。

这和你架构图里那两条线是一致的：**RepoFS 那层负责强制约束，Agent 那层只负责决定查什么。** 现在写的这套工具，就是 RepoFS 的第一块地基。
